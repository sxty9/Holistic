# Holistic

The umbrella. coreX owns identity and data, Solisuite owns the apps, Warpgate
owns the edge — and until now nobody owned *this instance as a whole*.

That gap is not theoretical. One answer — "which apps are active" — has to land
in three different configuration files: Warpgate's `apps[]` (which becomes DNS
and ingress), coreX's `instance.appOrigins`, and Solisuite's `apps[]` with both
`host` and `origin`. No single repository can keep those three in step, and the
third is generated by nothing today, which is why `appFor()` is inert without
somebody writing it by hand.

So Holistic owns the app catalogue as one source of truth and projects it into
three files, and it owns the setup process that produces them.

## What is here

    install.sh                 the user-facing installer — step two of two
    cmd/holistic-setup/        the setup process: a LAN listener that removes itself
    internal/claim/            who is allowed to configure a fresh instance
    internal/lan/              which addresses it answers on, and which requests
    internal/ledger/           what setup did, recorded before it does it
    internal/session/          the wizard's own session, disjoint from coreX's
    deploy/                    the systemd unit

## Installing

Two commands:

    curl -fsSLO https://<release>/install.sh
    sudo ./install.sh

It prints an address on your own network and a setup code. Open the address,
enter the code, and the instance is yours.

`--dry-run` says what it would do and changes nothing. `--code` mints a fresh
code if you lost the first one.

## The three decisions worth knowing about

**Setup answers on your local network, and it is guarded by a code.** A machine
that has just been installed has no accounts, so its setup page cannot ask
anyone to sign in — but that page creates the administrator, chooses the domain,
and is handed cloud credentials. Serving it openly means whoever reaches it
first owns the machine. A survey of eighteen comparable products found twelve
doing exactly that, with the CVEs to match. The installer already has something
nobody on the network has — a terminal — so it mints a code, writes it where
only root can read it, and prints it once. The code is spent when it is used and
deleted from disk.

This does not defend against someone who has claimed `holistic.local` and serves
a convincing copy of the page: `.local` names are unauthenticated and anyone on
the network can take one. The mitigations for that are that the installer
verifies its own published name resolves to the address it expects, and prints
the address when it does not.

**Nothing of yours is overwritten.** Setting up Holistic must not cost somebody
their website or their mail. Where setup finds something already standing where
it wanted to stand, it does not write — it reports what is there, quoted rather
than paraphrased, says why the two cannot both be true, and hands the decision
back. Every such report contains the sentence *"Warpgate changed nothing."*

That rule cannot be enforced by the credential. Cloudflare's DNS permission is
`Edit`, which is full create-read-update-delete-list over the zone; there is no
per-record binding and no "may add, may not replace". The narrow token bounds
the blast radius to one zone. Only the code bounds the behaviour inside it, and
both halves belong in any honest description of it.

**Setup removes itself.** The same act that marks the instance claimed disables
the unit, deletes the code, and ends every session. The unit carries
`ConditionPathExists=!/etc/holistic/claimed`, so it stays skipped even if
something enables it. What remains at `holistic.local` afterwards is a status
page — services, versions, where to sign in. Deliberately not a login form:
after the hand-off the instance's session cookie is scoped to the real domain
and marked `Secure`, so a form served over plain HTTP on a LAN name could never
succeed, and a login that cannot work is worse than none because it is
discovered in an emergency.

## Where it answers

The listener enumerates interfaces and binds them by name rather than
wildcarding. On a typical homeserver a wildcard bind would put an
unauthenticated-by-design setup page on the far end of a WireGuard tunnel, on
every container bridge, and — where the ISP delegates a routable prefix — on the
public internet. Measured on the development machine, `0.0.0.0` would have
included two globally routable IPv6 addresses.

Loopback is always bound, because `ssh -L` is the documented fallback for the
networks where `.local` does not survive: guest Wi-Fi with client isolation,
separated VLANs, and anywhere multicast is filtered.

## State of things

Working and covered by tests: the claim, the listener and its refusals, the
ledger, sessions, and the shell of the setup process.

Not built yet: the wizard's own steps, and the front end. The front end will be
its own Vite project with the same three dependencies as the Solisuite apps —
`@finessefx/ui`, `react`, `react-dom` — so setup and the thing it configures
look like one product without setup becoming a Solisuite app. It must not be
one: `appFor()` falls back to the default app for *any* unmatched Host, so a
setup page served by Solisuite would answer at every unclaimed hostname after
the hand-off.
